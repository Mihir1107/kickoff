# M18 plan: legal hold, destruction with a verifiable certificate, storage lock-down, upload quotas, the standalone verifier

Status: **proposed (2026-10-19), plan only, nothing built.** The decisions in §11 come first.

Scope: the items `docs/BACKLOG.md` marks **required before production** that need **no cloud
account**:
1. legal hold (blocks close, destruction and any retention shortening; placed, released, audited);
2. the post-close destruction workflow, with a certificate an outside party can verify;
3. bucket policies denying overwrites and delete markers, tested on MinIO;
4. a least-privilege storage identity (several, in fact: §3);
5. upload quotas for Slack exports;
6. the standalone `edisc-verify` package.

Not in scope (need a cloud account; they stay in the BACKLOG): AWS KMS, SSE-KMS on the buckets,
CloudTrail / S3 access logs, AWS's `s3:if-none-match` policy condition, the report image registry, the
1M soak. Two no-cloud items are close enough to this milestone that I propose adding them (D11):
retention for the tenant audit stream's anchors, and the staging bucket's prefix-limited access.

## 0. What exists, and what a spike on MinIO showed (verified 2026-10-19)

**In the code today:**
- **WORM.** Evidence is WORM, COMPLIANCE mode, with a rolling 90-day window. The retention-extension
  job extends it while the owner (matter, or client for exports) is open. Matters and clients close
  explicitly and can be reopened. A lapse is recorded as a `retention_gap` (ADR 0002). The
  application never deletes evidence.
- **One root identity.** The app talks to MinIO with the **root** credentials
  (`EDISC_S3_ACCESS_KEY`), from the API and every worker.
- **No hold.** Legal hold does not exist. ADR 0002 already promises that "once legal hold exists, a
  matter under hold cannot close". ADR 0017 promises that a render image is never deleted while a
  held matter has productions from it.
- **Nothing ever deletes a version.** Objects expire by retention, and nothing removes them in
  production (`infra/aws`: no expiration rule on evidence).
- **The verifier needs the workspace.** `edisc-verify` installs with `edisc-renderers` from the
  workspace, which pulls SQLAlchemy, asyncpg and aiobotocore.
- **No quotas.** Exports have per-upload limits (`slack_exports.limits`), but nothing per tenant.

**Spike on the test stack's MinIO** (`pgsty/minio` 2026-08-04, a scratch bucket, nothing committed):

| Check | Result |
|---|---|
| Legal hold on a version (no retention), then root deletes that version | **refused** ("WORM protected"), also for root |
| Hold cleared, then root deletes the version | deleted |
| COMPLIANCE retention running, root deletes the version | refused |
| Plain DELETE (no version id) on a held object | **succeeds: a delete marker**, for root and for any identity allowed `s3:DeleteObject` |
| Root clears a legal hold under a bucket policy that denies `s3:PutObjectLegalHold` to everyone | **cleared: root ignores bucket policies** |
| An IAM user without `s3:PutObjectLegalHold` clears a hold | Access Denied |
| An IAM user allowed `s3:PutObject` writes to an existing key without `If-None-Match` | **a new version** (a shadow; our pinned reads ignore it, `verify` reports it) |
| Bucket policy conditioned on `s3:if-none-match` | **rejected by MinIO**: "invalid condition key" |

Consequences for the design:
- Whoever holds `s3:PutObjectLegalHold` can undo a hold, and root can do anything. So the hold flag
  is only worth something if no running service holds root or the hold-clearing permission.
- The "deny PutObject without If-None-Match" policy from the BACKLOG **cannot be expressed on
  MinIO**. On MinIO the overwrite defence stays: If-None-Match in the code, VersionId pinning,
  shadow-version detection, and a periodic sweep (§3.3). The policy itself becomes a cloud item.

## 1. Legal hold

### 1.1 Model (migration 0047; FORCE RLS, grants, drift test, no DELETE)
- `legal_holds`: `id`, `tenant_id`, `scope_kind` (`matter` | `client`), `scope_id`, `reason` (required,
  bounded text, `RecordedText` on the way out), `reference` (optional: a docket or hold-notice id),
  `placed_by`, `placed_at`, `released_by`, `released_at`, `release_reason`. A release is final: a
  new hold is a new row. A trigger keeps identity immutable and lets `released_*` be written once.
- **Scope:**
  - A **matter** hold covers every evidence object behind the matter's jobs, deduplicated files
    included. It also covers the matter's productions (renders, natives, reports), the job seals
    and anchors, and the render/report images listed in `deploy/render-images.json` that produced
    them (ADR 0017).
  - A **client** hold covers every matter of the client, plus the client's Slack exports.
- `legal_hold_objects`: `(hold_id, evidence_object_id)`, written by the flagging workflow (§1.3).
  It records which pinned versions carry the S3 flag for which hold.
- An object is **held** while ANY unreleased hold covers it (dedup: one file can sit in two matters).
  `held_objects` is a view, the union of the active holds' scopes resolved through
  `job_items` → items → evidence, plus productions, plus exports. Every question "is X held?" goes
  through ONE function, `edisc_custody.holds.held(...)`, never a re-derived query.

### 1.2 What a hold blocks (each a check inside the same transaction as the action, plus a database guard where possible)

| Action | Today | Under hold |
|---|---|---|
| Close the matter / client | allowed when no job runs | **409 `legal_hold`**. Guard: a `BEFORE UPDATE` trigger on `matters`/`clients` refuses `closed_at` NOT NULL while a hold covers the row (the API check gives the clean error, the trigger catches any other path) |
| Destruction (§2) | does not exist | refused at request, re-checked per object right before each delete, and enforced by the S3 legal-hold flag on every version (§1.3) |
| Any shortening of retention | not possible today (reopen never shortens; COMPLIANCE never shortens) | stays impossible. The guard trigger forbids lowering `matters.retention_until` at all (today only by convention). If a future route ever lowers it, it must call `held()` |
| Retention extension | extends while the owner is open | **extends while the owner is open OR held** (a held matter is open anyway; a client hold also keeps its closed-but-not-yet-destroyed exports extended) |
| Tenant offboarding | does not exist | must call `held()`: refuse (noted for the backlog item) |
| Render image retirement (ADR 0017) | manual | refused while a held matter has productions from the image |

A hold does **not** block new jobs, renders, reports or reads: preservation, not freezing.

### 1.3 The S3 flag (defence in depth, D2)
- **Why:** the database hold alone protects only as long as the database and the extension job are
  honest. With the flag, a version under hold cannot be deleted by anyone without
  `s3:PutObjectLegalHold`, root included (spike row 1), even after its retention lapses.
- **The workflow:** `LegalHoldWorkflow` (queue `holds`, a worker running as the **hold identity**,
  §3) resolves the scope page by page (keyset on `evidence_objects.id`). For each pinned version not
  yet flagged for this hold, it calls `PutObjectLegalHold(ON)`, then inserts the
  `legal_hold_objects` row. The checkpoint is the last id done, in the same transaction as that
  page's rows. Rate-limited like any S3 bulk work. Every page appends a `hold_objects_flagged`
  event (Merkle root over the page's `(evidence id, key, version, sha256)`).
- **Objects linked to a held matter after placement:** new jobs, renders, reports and dedup hits
  are flagged by the same workflow. It re-runs on a schedule (`flag-held-objects`, 15 min), and on
  `job_finalized` / `render_sealed` / `report_sealed` for a held matter. Until a flag lands, the
  database hold already blocks destruction. The gap is visible: `GET /v1/legal-holds/{id}` reports
  `objects_flagged` / `objects_in_scope`.
- **Release:**
  - The database release commits first; the hold is released the moment it commits.
  - The workflow then clears the flag ONLY on versions no other active hold covers, checked per
    page inside the transaction that records the clearing (`hold_objects_cleared` event).
  - A version still covered by another hold keeps its flag, and its `legal_hold_objects` row moves
    to that hold.
- The flag never replaces the database check, and vice versa. Destruction refuses on either.

### 1.4 API, permissions, audit (ADR 0013/0016 conventions)
- New permissions:
  - `legal_hold.place`: tenant_admin, matter_manager (at the matter or client).
  - `legal_hold.release`: tenant_admin only (D3).
  - `legal_hold.read`: tenant_admin, matter_manager, client_admin, auditor.
- Routes:
  - `POST /v1/matters/{id}/legal-holds`, `POST /v1/clients/{id}/legal-holds`: body `{reason,
    reference?}`, recent sign-in, audited `legal_hold_placed`.
  - `POST /v1/legal-holds/{id}/release`: body `{reason}`, recent sign-in, and (D3) a second tenant
    admin's approval: `release_requested`, then `release_approved` by another principal within 72 h,
    else it expires.
  - `GET /v1/legal-holds`: cursor list, filterable by scope.
  - `GET /v1/legal-holds/{id}`: flag progress.
  - `GET /v1/matters/{id}` / clients: add `held: bool`.
- Every placement, release request, approval, expiry and release is a custody event in the tenant
  stream (`audit.legal_hold_*`) and is anchored.
- Alerts:
  - placing or releasing notifies every tenant admin and the matter's managers (one alert per
    event);
  - a release starts a **cooling-off period** (D4, default 7 days) during which nothing it
    uncovered may be destroyed.
- The collection report and the job package state the holds that covered the job, from the chain:
  the job package gets `holds.jsonl`, and `edisc-verify` recomputes it. That needs a report renderer
  bump (D9).

## 2. Destruction, and its certificate

### 2.1 When destruction may run (all of these, checked at request AND per object)
1. The owner is closed: the matter, or the client for exports and every matter of the client.
2. No active legal hold covers the object, and the cooling-off period of any hold released over it
   has passed.
3. **Nothing else still owns the object.** A deduplicated file linked by a job of any other matter
   that is open, or not yet destroyed, is **retained**. The certificate lists it as retained, with
   reason `referenced_elsewhere` and a count, never the other matter's name (D8).
4. Its retention has lapsed **on the storage's clock**: `HeadObject` on that version shows
   `retain-until` < the response's `Date`. A refusal from the store ("WORM protected") means "not
   yet", never a failure, and is reported as `still_locked`.
5. A tenant admin requested it (D5: never automatic), with a reason, recent sign-in and a second
   admin's approval (D3).

### 2.2 What is destroyed, and what is kept
- **Destroyed:**
  - **Storage:** every version under each covered key (`ListObjectVersions` on the exact key,
    shadows and delete markers included, each deleted by version id). This covers:
    - raw pages, files and archive-entry exports;
    - the export zips;
    - productions (`.rsmf`, natives) and report files;
    - the job's seal objects.
  - **Database content (D6), through a definer function owned by a separate `edisc_destroyer` role
    (the app role still cannot delete or update):**
    - item text and names in `items` / `item_derivations`;
    - `export_conversations` names;
    - the directory entries of a destroyed client's connections.
- **Kept:**
  - the custody chains: hashes, ids, counts, no content;
  - the registry rows, with status `destroyed`, `destroyed_at`, and the destroying custody event;
  - anchors of the destruction stream, and the certificate.
- **Proposed, not yet agreed (D7): the anchors of destroyed job streams are deleted too.** They
  carry only hashes, but they are under the matter's keys.

### 2.3 The workflow (`DestructionWorkflow`, queue `destruction`; the worker runs as the **destruction identity**, §3, and is the ONLY process with `s3:DeleteObjectVersion`)
1. **Plan.** One transaction: the request row moves `approved → planning`, and a snapshot of the
   candidate set is written page by page:
   - `destruction_objects`: id, key, version, sha256, size, owner, decision `destroy` | `retain`
     with reason;
   - each page has a checkpoint and a `destruction_planned` event (Merkle root over the page).
2. **Mark.** Per page: registry rows go `complete → destroying` in the transaction that appends
   `objects_destroying`. **The dedup path refuses to link a `destroying` or `destroyed` row**
   (§2.4).
3. **Delete.** Per object, outside any transaction:
   - re-check `held()` and the ownership check (the database answer);
   - `HeadObject` the pinned version and check that the lock has lapsed on the store's clock;
   - `ListObjectVersions` on the key and delete every version by id;
   - list again: **zero versions** must remain;
   - then one transaction: registry `destroyed`, a `destruction_objects` row with the deleted
     versions and the store's response request ids, and an `object_destroyed` event (batched per
     page, Merkle root over the rows).
   - A version that reappears (a write racing the delete) fails the object loudly
     (`destruction_incident`, an alert). It is never silently re-deleted.
4. **Purge.** The database content of the destroyed items (D6), per page, each with its event.
5. **Certify** (§2.5), seal the destruction stream, anchor it, `audit.destruction_completed`.
- **Resumable at every step:** the checkpoint is the database (CLAUDE.md principle 5). A delete of
  an already-deleted version is confirmed only by the follow-up listing, never by a 404 alone.

### 2.4 Races that must be impossible
- **A collection deduplicates onto a file being destroyed.** `destroying`/`destroyed` rows are not
  dedup hits. The writer treats the content key as absent and re-uploads after destruction under the
  per-key advisory lock (`_content_lock`). A **new registry row** gets a `generation` (the unique key
  becomes `(tenant, key, generation)`), so the destroyed row and its certificate entry stay true.
  Until destruction of that key completes, the writer waits on the lock: delete and upload never
  interleave.
- **A hold placed during destruction.** The per-object re-check runs in the delete step's
  transaction, which takes `FOR SHARE` on the hold scope. Placing a hold takes the conflicting lock
  on the matter row. So either the hold is placed first and the object is skipped (`retain`, reason
  `held`), or the object was already deleted before the hold, which the hold's own record then
  shows. The certificate states which.
- **Reopen during destruction.** Reopening a matter whose destruction has started is refused (409
  `destruction_in_progress`). After completion, a reopened matter has no evidence. Its jobs stay
  `sealed`, and the job package then fails to fetch objects with a clear "destroyed on <date>,
  certificate <id>" error.

### 2.5 The certificate (an outside party verifies it without our database)
- **Contents:** `edisc-destruction-certificate/1`, a zip written through `edisc_custody.zipwriter`.
  - `certificate.json`, canonical:
    - tenant, scope, request, approvers, reasons, times;
    - per destroyed object: evidence id, key, every deleted version id, SHA-256, size, owner,
      retain-until, deletion time, the store's request ids;
    - per retained object: the reason and a count;
    - the destruction stream's head and seal.
  - `stream.jsonl`: the destruction custody stream.
  - `anchors.jsonl`: the stream's anchors, listed from S3.
  - `signature.jws`: a detached JWS over the SHA-256 of `certificate.json`.
- **Signed** with a platform certificate key (KMS, separate from the client-auth key; D7). The key
  is published at `/.well-known/edisc-certificate-jwks.json`, and its fingerprint is printed in
  `docs/VERIFYING.md` per environment.
- **Retention:**
  - the certificate is stored as WORM evidence under `t/{tenant}/destruction/{id}/`, with its own
    retention: tenant setting `certificate_retention_years`, default 10 (D7);
  - the destruction stream's anchors are retained the same way;
  - both outlive the destroyed evidence, by design.
- **`edisc-verify --destruction <cert.zip>`** checks:
  - the JWS (the key given with `--key`, or the published JWKS fetched with `--fetch-key`);
  - the stream's hash chain and Merkle roots, and that every listed object appears in exactly one
    `object_destroyed` batch;
  - the anchors.
- **With `--job-package <pkg>`** (packages the party received before destruction), it also checks:
  - every object of those jobs is either destroyed (same hash and key) or retained with a reason;
  - nothing in the packages is unaccounted for.
- **What it cannot prove, stated in VERIFYING.md:** that the bytes are gone from storage. It proves
  what we recorded deleting, signed and anchored. The storage-side proof is the store's audit log
  (CloudTrail, a cloud item).

## 3. Storage identities, bucket policies (tested on MinIO)

### 3.1 Identities (MinIO users + IAM policies created by `infra/minio/init.sh`; AWS roles later)

| Identity | Used by | Evidence bucket | Staging bucket |
|---|---|---|---|
| `edisc-app` | API, collection/export/render/report workers | `PutObject`, `GetObject(Version)`, `GetObjectRetention`, `PutObjectRetention` (extend), `GetObjectLegalHold`, `ListBucketVersions`, multipart create/upload/complete/**abort**, `HeadObject` | Put/Get/Delete under its prefixes `t/`, `exports/` only |
| `edisc-hold` | `holds` worker only | `PutObjectLegalHold`, `GetObjectLegalHold`, `GetObjectVersion`, `ListBucketVersions` | none |
| `edisc-destroy` | `destruction` worker only | `DeleteObjectVersion`, `ListBucketVersions`, `GetObjectRetention`, `GetObjectLegalHold`, `HeadObject` (+ `PutObject` under `t/*/destruction/` for the certificate) | none |
| root | provisioning (`init.sh`) only | (everything) | (everything) |

- Nobody gets `s3:DeleteObject` (the delete marker), `s3:BypassGovernanceRetention`, or bucket
  configuration permissions.
- Root credentials leave the application settings entirely. `Settings` gets three credential pairs,
  and each process loads only its own: a worker started with `--holds` or `--destruction` refuses to
  run any other queue.
- `make test-production-install` checks that the API process has no hold or destroy credentials in
  its environment.

### 3.2 Bucket policies (explicit denies, the second layer)
- **Evidence bucket:**
  - deny `s3:DeleteObject`, `s3:DeleteObjectVersion`, `s3:PutObjectLegalHold`,
    `s3:BypassGovernanceRetention`, `s3:PutBucket*`, `s3:DeleteBucket*` to every principal except
    the identity that needs it. MinIO policies support `aws:username`, so the exceptions are written
    as `StringNotEquals aws:username`;
  - deny `s3:PutObject` outside `t/` and `custody-anchors/`.
- **Staging bucket:** deny everything to everyone but `edisc-app`.
- **"Deny PutObject without If-None-Match":** not expressible on MinIO (spike). AWS supports
  `s3:if-none-match`: written into `infra/aws/evidence-bucket-policy.json` and marked "confirm on
  AWS" (BACKLOG, cloud).

### 3.3 Tests (all on the test stack's MinIO)
- **The whole integration suite runs as `edisc-app`** (the fixtures load the app identity, never
  root). Any missing permission fails a test somewhere: that is the point.
- **Negative matrix** (`tests/integration/evidence/test_identities.py`): every identity × every
  forbidden action (delete marker, version delete, retention shorten, hold set/clear, bucket config,
  write outside its prefixes, read the other bucket). Each must fail with AccessDenied. Each allowed
  action succeeds once (positive controls).
- **Overwrite sweep:** `check-shadow-versions` (maintenance, daily) lists versions of recently
  written keys. Any version other than the pinned one is an `evidence_shadow_version` episode with
  an alert. This is the MinIO-side defence for the missing If-None-Match policy. Tested by writing a
  shadow as `edisc-app` without the header.

## 4. Upload quotas (Slack exports, ADR 0014)
- **Per-tenant settings** (D10: set by the operator CLI `python -m edisc_api.admin quota`, readable
  by tenant admins, never raised by them):
  - `export_bytes_in_flight` (default 200 GiB: uploads not yet ready or rejected);
  - `export_bytes_stored` (default 2 TiB: validated exports of open clients plus in-flight);
  - `export_uploads_concurrent` (default 3).
- **Enforced:**
  - **at create:** declared size against all three, under a `FOR NO KEY UPDATE` lock on a per-tenant
    `tenant_quota_usage` row, in the create transaction. 409 `quota_exceeded` with the limit and the
    usage (server state, A8-safe), audited `export_quota_refused`;
  - **at every part PUT:** received bytes may never exceed the declared size (already 413).
- **Released** when an upload is rejected, expires (the 7-day staging rule, swept by
  `expire-export-uploads`, which marks it `rejected` / `upload_expired`), or its client is
  destroyed. A validated export moves from in-flight to stored.
- **Usage** is recomputed from the rows by a daily check. A drift is an episode with an alert, never
  silently corrected.
- **Tests:** a race of N concurrent creates at the limit (exactly the allowed number succeed),
  release on reject and expiry, no quota leak across tenants, A8 no-echo for the 409.

## 5. The standalone `edisc-verify` (BACKLOG item, D12)
- **The package:** a new workspace member `packages/verify` (distribution `edisc-verify`, module
  `edisc_verify`) **owns** the offline code:
  - the canonical JSON and lone-surrogate pieces of `edisc_core`;
  - from `edisc_custody`: `merkle`, `chain` (`ChainVerifier`), `package`, `cli`, `archive`,
    `package_archives`, `rsmf_check`, `render_files`, `report_files`, the job package readers;
  - the zip reader;
  - `edisc_renderers.report.model` + `recompute`;
  - the new certificate checks.

  The product packages import from it (product → verifier, never the reverse). The old module paths
  stay as re-exports for one release, so the mutation catalog and the tests move in the same commit.
- **Boundary:**
  - the purity tests extend to the whole distribution: its modules import only the stdlib and its
    own pinned dependencies (today: `jsonschema` for the RSMF manifest, `jwcrypto` or `cryptography`
    for the certificate JWS: D12);
  - no SQLAlchemy, asyncpg, aiobotocore, temporalio or FastAPI.
- **CI job `verifier-standalone`:**
  - builds the wheel (hatchling, `SOURCE_DATE_EPOCH` = commit time) twice and compares SHA-256;
  - installs it into an EMPTY venv from the wheel + a hashed requirements file, `--no-index` after
    download;
  - verifies the corpus job package, a render package, a report package (with `--job-package`
    recomputation), a destruction certificate, and every tamper case;
  - the outputs must equal the in-tree verifier's, byte for byte.
- **Release:**
  - a `verifier-v*` tag publishes the wheel, its SHA-256 and the commit;
  - VERIFYING.md's install section points to it;
  - the verifier states the formats it reads (custody `/1`-`/3`, render `/1`-`/3`, report `/1`,
    destruction `/1`).

## 6. Threat model (attack → defence → the test that proves it)

| # | Attack | Defence | Test |
|---|---|---|---|
| T1 | Leaked app credentials delete or hide evidence | `edisc-app` has no delete; the bucket policy denies it; WORM; pinned reads ignore markers | identity matrix; delete marker as app refused |
| T2 | Leaked app credentials overwrite a key | If-None-Match in code; pinned VersionId; shadow sweep + alert (MinIO cannot deny by policy) | shadow written without the header → episode + alert; reads still serve the pin |
| T3 | Compromised API process releases a hold and destroys | Release: tenant admin + recent sign-in + second admin; cooling-off; API holds no hold/destroy credentials; destruction is a separate worker identity | release without approval refused; destruction inside cooling-off refused; API env has no hold/destroy keys |
| T4 | A single rogue tenant admin | two-person rule on release and destruction (D3); alerts to every admin; everything anchored | one admin cannot both request and approve (same principal refused) |
| T5 | Destroying an object another matter still uses (dedup) | ownership check at plan and per object, in the delete transaction | dedup file linked by an open matter → `retain`; certificate lists it as retained |
| T6 | Collection dedups onto a file mid-destruction | `destroying` rows are not dedup hits; content lock; generations | crash matrix + a racing collection test: the new collection re-uploads and gets a new generation; the certificate stays true |
| T7 | Hold placed while destruction runs | per-object re-check under the lock order of §2.4 | barrier between mark and delete; place a hold; the object is retained `held` |
| T8 | Incomplete destruction (shadow versions, markers, natives, report files, exports, staging) | list every version per key, delete by id, list again; staging expiry; content purge | shadow + marker present before → zero versions after; DB content gone; certificate lists every version |
| T9 | Destruction before the lock lapses (clock skew) | the store's clock decides (`HeadObject` Date vs retain-until); refusal = `still_locked` | object with seconds of retention left: reported, retried later, never failed |
| T10 | A forged certificate | JWS with a KMS key + anchored stream + Merkle roots | `edisc-verify --destruction`: tampered JSON, wrong key, removed object, reordered stream all FAIL |
| T11 | A certificate that hides a retained object | every object of the scope is destroyed or retained-with-reason; `--job-package` cross-check | drop one retained row → FAIL |
| T12 | Root credentials used at runtime | root only in `init.sh`; settings refuse root's access key outside local/test/ci tooling | startup refusal test |
| T13 | Quota bypass by racing creates or lying sizes | row lock on the usage row; per-part byte checks | N concurrent creates at the limit |
| T14 | Cross-tenant hold or destruction | RLS, ids resolved within the tenant, 404 | tenant isolation tests for every new route and table |
| T15 | A tampered standalone verifier | reproducible wheel, published SHA-256, hashed requirements | CI builds twice, compares hashes |
| T16 | Hold bypass by close/reopen or retention edits | close trigger; retention never lowered (trigger); reopen during destruction refused | trigger refuses a direct SQL close under hold |

## 7. Crash points (each with a test that kills there: SIGKILL of the worker or the in-process barrier, then resume)
- **Hold placement:** after the database commit, before the first flag; mid-page (flags set, rows
  not written: the next run re-sets them idempotently, `PutObjectLegalHold(ON)` twice is harmless);
  after the last page, before progress is recorded.
- **Hold release:** after the database release, before any flag is cleared (the database release
  already governs); mid-page (some flags cleared). A version covered by another hold must never be
  cleared: tested with two overlapping holds and a kill between their pages.
- **Destruction:**
  - after planning, before marking;
  - after marking, before the first delete;
  - **between deleting some versions of one key and the rest**;
  - after all versions are deleted, before the `object_destroyed` transaction;
  - mid content purge;
  - after the certificate is written, before the seal;
  - after the seal, before the anchor.

  Each resumes to the same certificate bytes, with zero versions left and no event repeated.
- **Quota:** after the create transaction, before the upload starts (the reservation is released by
  expiry); after `complete`, before validation (in flight, then stored).

## 8. Mutation plan (round `m18`; one catalog entry each, the named test must fail)
- **Holds:**
  - close allowed under hold (API check removed; then the trigger removed separately);
  - extension stops for a held, closed client's exports;
  - `held()` ignores client-level holds;
  - a release clears a flag another hold still needs;
  - flags not applied to objects linked after placement;
  - release without the second approver;
  - same principal approves;
  - cooling-off skipped.
- **Destruction:**
  - deletes a dedup file another matter uses;
  - skips the per-object hold re-check;
  - trusts the database clock instead of the store's;
  - deletes only the pinned version (a shadow left);
  - treats a 404 as success without listing;
  - the `destroying` row stays a dedup hit;
  - the purge leaves `item_derivations` text;
  - the certificate omits retained objects;
  - the Merkle root is over the wrong field set.
- **Certificate verification:** a tampered certificate passes because the JWS is not checked; it
  passes because the anchors are not compared.
- **Identities:**
  - `edisc-app` granted `s3:DeleteObject`;
  - the API loads the destroy credentials;
  - a worker with `--destruction` also polls another queue;
  - the shadow sweep never alerts.
- **Quotas:** the check outside the lock (race); usage not released on reject or expiry; the 409
  echoes the declared size of the request.
- **Verifier:**
  - an import of `sqlalchemy` inside the distribution;
  - an unpinned dependency;
  - a non-reproducible timestamp in the wheel.

## 11. Decisions needed from you (my recommendation first)
- **D1 Hold scope.** Matter and client. **Recommended: both**, nothing finer now. Custodian-level
  holds belong with Phase 3's custodian model.
- **D2 S3 legal-hold flags in addition to the database hold.** **Recommended: yes.** It is the only
  protection that survives a compromised database or a stopped extension job (spike: it stops even
  root). Cost: one `PutObjectLegalHold` per version (~10M calls for a 10M-object matter, done in the
  background), a `holds` worker, an identity.
- **D3 Two-person rule** for releasing a hold and approving a destruction: a second tenant admin
  approves within 72 h, and the same principal can never both request and approve. **Recommended:
  yes for both.** Alternative: one admin + recent sign-in + alerts only. Simpler, but one compromised
  admin account then suffices.
- **D4 Cooling-off** after a release before anything it uncovered may be destroyed. **Recommended:
  7 days**, a tenant setting (minimum 7, maximum 90).
- **D5 Destruction trigger.** **Recommended: manual only** (request + approval), never automatic at
  lapse. Alternative: a tenant opt-in to automatic destruction N days after lapse.
- **D6 Database content purge.** **Recommended: purge content columns** (message text, names,
  derivations; directory entries of a destroyed client) and keep hashes, ids and chains. This is a
  deviation from "nothing is deleted" (§10). Alternative: storage-only destruction, with the database
  copy kept until tenant offboarding. In my view that does not honour a destruction request.
  Database backups (PITR) keep content until their own expiry; the certificate must say so.
- **D7 Certificate.** **Recommended:**
  - format: JSON + detached JWS (ES256 or RS256 on a dedicated KMS key; locally the local KMS);
  - retention: 10 years (tenant setting);
  - destroyed jobs' anchors deleted with them; the destruction stream's anchors kept as long as the
    certificate.

  A human-readable PDF can come later from the report toolchain.
- **D8 Dedup retained objects** are listed as retained with a count, never the other matter's name.
  **Recommended.**
- **D9 The report states holds.** A report renderer bump with new goldens (report and PDF in the
  image). **Recommended: yes, in step 7.**
- **D10 Quotas.**
  - Who sets them: **recommended: the operator CLI only**; tenant admins see usage.
  - Defaults: 200 GiB in flight, 2 TiB stored, 3 concurrent uploads.

  Your numbers if you have contract figures.
- **D11 Add two no-cloud items:**
  - retention extension for the tenant audit stream's anchors (required before production; the
    certificate's anchors live in that world);
  - the staging bucket's prefix-limited access (falls out of §3).

  **Recommended: yes.**
- **D12 Verifier packaging.** **Recommended: a new package that owns the offline code** (product
  imports from it) rather than build-time vendoring (copies drift). The JWS library is `jwcrypto`
  vs. hand-rolled over `cryptography`: **recommended `cryptography` only** (already in the lock
  file, a smaller dependency surface for the outside party).
- **D13 Principles (§10).** Your explicit yes to the three wording changes before step 6.
