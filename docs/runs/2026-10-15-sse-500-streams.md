# 500 concurrent job streams (M17 step 5, decision D4), 2026-10-15

`scripts/measure_sse.py` on the ephemeral test stack (`make test-env-up`), this laptop (Apple
silicon, Docker Desktop). The REAL API app in-process (ASGI), production stream settings (poll 1 s,
re-check 15 s, queue 64, 10 streams per principal), its own fixed 40-connection pool; 50 principals
(tenant-wide reviewers) hold 10 streams each. Every 5 s each job's next unit is settled (row + chain
event, as the pipeline writes them) through a SEPARATE engine, so the statements counted are the
stream's own. Streams open in a ramp of 50.

| | 500 streams on 50 jobs | 500 streams on 500 jobs |
|---|---|---|
| measured | 63 s, 12 settle rounds | 88 s, 2 rounds (500 serial settles per round) |
| ramp to 500 open streams | 15.3 s | 19.7 s |
| API statements per second | 298 (0.60 per stream) | 1,062 (2.12 per stream) |
| deliveries / expected | 6,000 / 6,000 | 1,000 / 1,000 |
| latency settle commit -> each subscriber: p50 / p99 / max | 604 / 1,097 / 1,196 ms | 651 / 1,693 / 2,194 ms |
| Python-allocated bytes per open stream (tracemalloc) | 72,875 | 75,444 |
| process RSS max | 293 MiB | 260 MiB |

Reading it:
- **Cost follows jobs, not streams** (D4): one `HEAD` statement per job per second while it has
  subscribers, plus four to read a change (unit events, units, counts, pauses) and, per stream, a
  re-check every 15 s (the session or principal, cached per caller, and `authorize`). Ten tabs on
  one job cost about what one costs; 500 different jobs cost about 1,000 statements a second on
  one API process. Batching every feed's `HEAD` into ONE statement per tick is the next step if a
  process ever holds hundreds of distinct jobs (BACKLOG).
- **Latency is the poll interval:** p50 about half a second, p99 about one poll plus the read; at
  500 jobs the p99 grows to 1.7 s because each tick runs 500 polls through a 40-connection pool.
- **Memory is bounded by the queue, not the job:** about 72-75 KB of Python allocations per open
  stream, which includes the measuring client's own buffers in the same process; the producer never
  waits for a client (a full queue ends that stream with `slow_consumer`, tested).
- **Found by this measurement:** the first runs opened all 500 streams at one instant and the
  API's Redis client (the authentication throttle) raised `MaxConnectionsError` past redis-py's
  default 100 connections: an unhandled 500 per request of the burst. The API's Redis pool is now
  fixed and blocking (`redis_max_connections` 50, a bounded wait `redis_pool_timeout_seconds` 10,
  then 503 `service_busy`), tested in `tests/integration/api/test_pool_exhaustion.py`.
- Not measured here: a real network between client and server (in-process ASGI), several API
  processes (each polls its own jobs: N processes x jobs), Postgres server CPU (the stack shares
  the laptop).
